# 2070 推理速度研究（2026-09-27）

机器：10.1.2.16（`bolt-remote`）· RTX 2070 / sm_75 / 8 GB / 峰值带宽 448 GB/s
CPU：Intel i7-6700K @ 4.00 GHz / 8 线程（**不是瓶颈**，`-t 4` 与 `-t 8` 无差异）
模型：`translategemma-4b-it.i1-Q4_K_M.gguf`（2.49 GB）+ `translategemma-4b-LoRA-COK-T4.gguf`（238 MB）
生产配置：`-c 1024 --parallel 2 -ctk f16 -ctv f16` + `translategemma-official.jinja`

**本文件记录四批实验。结论是：这台卡已跑到实际上限，没有剩下的大杠杆。**

---

## 0. 先说测量方法：我最初的数字全被污染

早期测到 decode **19.87 - 27.25 ms/tok、抖动 ±40%**，据此得出「有效带宽只有峰值 28%」「抖动无法解释」。
**全错。** 三个污染源：

1. **`:8081` 常驻**（基座模型，3008 MiB）与生产实例（3056 MiB）共享同一张 8 GB 卡
2. 我停服务时**只停了 `:8080`**，`:8081` 一直在跑
3. 我自己的 curl 循环本身就是「生产流量」

**干净环境下的真相**：

| | 污染值 | 干净值 |
|---|---|---|
| decode | 19.87 - 27.25 ms/tok | **13.1 ms/tok** |
| 抖动 | ±40% | **±0.4%** |
| 有效带宽 | 208 GB/s 的 28% | **208 GB/s = 峰值 46%** |

`:8081` 停掉后显存从 6064 MiB 降到 **1 MiB**，全部指标立刻稳定。

**教训：在这台机器上做任何测量前，先 `nvidia-smi --query-compute-apps` 确认只有被测实例占卡。**

## 1. 常规开关：全部无效

长段落翻译（389 字符 → ~250 token 输出），每配置 3 次：

| 配置 | ms/tok |
|---|---|
| **A 基线**（生产配置）| 13.11 / 13.16 / 13.15 |
| B `-fa on` | 13.15 / 13.13 / 13.16 |
| C `-b 2048 -ub 2048` | 13.15 / 13.17 / 13.21 |
| D `-fa on -b 2048 -ub 2048` | 13.21 / 13.20 / 13.19 |
| E `-t 4` | 13.20 / 13.19 / 13.20 |
| F `-t 8` | 13.19 / 13.19 / 13.20 |

**差异都在 ±0.4% 的噪声内。** 这与 sm_70 完全不同（V100 上 `-ub 2048` 是 +20~37%）：
Turing 的 `should_use_mmq` 提前 `return true`，走 mmq 融合路径，没有重复解压。

`-fa` 无差异是因为上下文只有 1024，attention 不是瓶颈。

## 2. LoRA 的真实代价：+37%（最大单项成本）

| 配置 | 长段落 ms/tok | 短句 ms/tok |
|---|---|---|
| **无 LoRA** | **9.62 / 9.63** | **9.1 ×4** |
| **有 LoRA（生产）** | 13.13 / 13.16 | 12.5 ×4 |

**12.5 / 9.1 = +37%。**（比我早先测的 +23% 更大，因为那次有污染。）

**代价构成**：LoRA 权重 238 MB，按 208 GB/s 只需 1.14 ms，但实测多出 **3.4 ms**。
差的 2.3 ms 是 **476 个小 matmul 的效率损失** —— 每个只读 655 KB，远不足以喂满带宽。

**为什么不能靠合并去掉**：要保住 rank-128/alpha-128 的小 delta 就必须用 Q6 精度，
字节从 2.49 GB 涨到 3.19 GB（+28%），正好抵消省下的内核。四组量化实测（Q4 ❌崩 / Q5 ❌崩 / Q6 ✅保住但不快）
见 `2070-tg-lora-调查-2026-09-26.md` 第 3 节。

**唯一理论上的修法**：把共享输入的适配器合并成一次 matmul（q/k/v 的 A 矩阵拼成 `[384 x hidden]`，
gate/up 拼成 `[256 x hidden]`），可省 14 个 matmul 中的 3 个 = LoRA 成本的 ~21% = **整体 ~4%**。
需要改 `src/llama-graph.cpp:1534 build_lora_mm`。收益太小，不建议做。

## 3. n-gram 投机解码：对长输出有效，对生产负载无效

这个构建支持 `ngram-simple` / `ngram-map-k` / `ngram-map-k4v` / `ngram-mod` / `ngram-cache`
（**都不需要 draft 模型**）。`draft-*` 系列需要同词表 draft 模型，见第 4 节。

| 配置 | 长段落（3 次连发）| 短句（4 次连发）|
|---|---|---|
| A 基线 | 13.48 / 13.11 / 13.08 | 12.5 ×4 |
| B `ngram-simple` 默认 | 13.15 / 13.17 | 12.5-12.6 |
| C `ngram-map-k` | 13.21 / 13.22 | 12.5-12.6 |
| D `ngram-map-k4v` | 13.20 / 13.20 | 12.5-12.6 |
| E `ngram-cache` | 13.22 / 13.21 | 12.5-12.6 |
| F `ngram-mod` 默认（n-min=48）| 13.54 / 13.13 / 13.13 | 12.5 ×4 |
| **G `ngram-mod` n-min=16** | 13.48 / **7.40** / **8.18** | 12.5 ×4 |
| **H `ngram-mod` n-min=8** | 13.57 / **7.03** / **7.91** | 12.5 ×4 |
| I `ngram-simple` n=4 m=8 | 13.62 / 13.13 / 13.13 | 12.5 ×4 |

**结论：**
- `ngram-mod` 降门槛后在**重复的长输出**上到 **1.8x**（13.5 -> 7.0 ms/tok）
- **短句（生产实际负载，10-20 token 输出）完全无效** —— 输出太短，够不到 n-gram 门槛
- 其余四种 n-gram 变体在两种负载上都无效果

**所以对翻译服务没用。** 除非将来有「长文本 + 高重复」的负载。

## 4. draft 模型投机：被词表堵死

| 模型 | 词表 | 能否当 draft |
|---|---|---|
| 目标 `translategemma-4b` | **262208** | — |
| `gemma-4-E2B-it-qat-UD-Q4_K_XL.gguf` | 262144 | ❌ 差 64 |
| `Hy-MT2-1.8B-Q4_K_M.gguf` | 120818 | ❌ 完全不同 |

机器上只有这三个候选，**没有词表匹配的小模型**。要做 draft 投机必须先找一个同词表的
gemma3 系小模型（或自己训一个）。

## 5. 并发：`--parallel 2` 已是最优

8 条不同短句，n 个并发同时发出：

| 配置 | 慢请求耗时 | 聚合 tok/s | 中位延迟 | 最大延迟 |
|---|---|---|---|---|
| par=1 并发=1 | 790 ms | 17.7 | 790 | 790 |
| **par=2 并发=2** | 316 ms | 63.2 | 262 | 316 |
| **par=2 并发=4** | **346 ms** | **101.2** | **285** | 346 |
| par=4 并发=4 | 500 ms | 70.0 | 406 | 500 |
| par=4 并发=7 | 834 ms | 73.2 | 465 | 834 |
| par=7 并发=7 | 731 ms | 82.1 | 634 | 731 |

**加 slot 反而更差**（延迟涨 2 倍多）。`--parallel 2` 下 4 个并发请求的中位延迟只比 2 个并发高 9%
（285 vs 262 ms）—— 说明 2 个 slot 已经能很好地把请求配对成 batch。

**顺带推翻一个我提过的「修复」**：我曾说网关 `MAX_CONCURRENCY=7` 与服务端 `--parallel 2`
错配导致超时，应该调大 `--parallel`。**错了。** 实测并发 4 时中位延迟只有 285 ms，
离网关 2500 ms 超时有 10 倍余量。**真实原因是 JSON 输出过长**（51 token vs 官方格式 9 token，见下节）。

## 6. 唯一真正有效的大杠杆：输出长度（客户端侧）

| 请求形态 | 输出 token | predicted_ms |
|---|---|---|
| 带 `response_format` JSON schema | 51 | ~1400 |
| **官方格式（纯译文）** | **9** | **~108** |

**5.7 倍 token 差、13-17 倍延迟差。** 官方模板本来就输出纯译文
（`Produce only the <tgt> translation...`），任何客户端加 `response_format` 都是在逼模型做没训练过的事。

**这是唯一值得做的优化，而且不需要改 llama.cpp。**

## 7. 总表：哪些路走不通

| 杠杆 | 结论 | 依据 |
|---|---|---|
| `-fa on` | ❌ 无效 | 13.15 vs 13.11 |
| `-b/-ub 2048` | ❌ 无效（Turing 走 mmq）| 13.15 vs 13.11 |
| 线程数 `-t` | ❌ 无效 | 13.19 vs 13.11 |
| KV cache 类型 | ❌ 无关（上下文仅 1024，KV ~4 MB）| — |
| n-gram 投机 | ❌ 短句无效（长输出有效 1.8x）| 12.5 不变 |
| draft 模型投机 | ❌ 无同词表小模型 | 262208 vs 262144 |
| 合并 LoRA | ❌ Q4 崩质量 / Q6 字节抵消 | 见另一份文档 |
| 折 scale 进 `lw->b` | ❌ `GGML_CUDA_FUSE_CHAIN` 已融合 | `ggml-cuda.cu:3616-3619` |
| 调大 `--parallel` | ❌ 更差 | par=7 延迟 634 vs par=2 的 285 |
| 量化更小（Q4_K_S 等）| ⚠️ 未测，预计 <5%（46% 带宽占用下收益有限）| — |
| **缩短输出（去 `response_format`）** | ✅ **5.7x** | 51 -> 9 token |

## 8. 为什么 46% 峰值带宽已经是「正常」

有效带宽 = (2.49 GB 权重 + 0.238 GB LoRA) / 0.0131 s = **208 GB/s**，占 448 GB/s 峰值的 **46%**。

Q4_K_M 解码要在读权重的同时做反量化，且 4-bit 访问模式无法完全合并，46% 是 Turing 上的合理水平。
对比 V100（900 GB/s）在 27B IQ4_XS 上能到 ~60%，但那是更大模型、更多 SM。

**要继续往上走只能靠减少字节（更小量化）或增加每字节的 token 数（投机）——
而投机这条路已被第 3、4 节堵死。**

## 9. 复现

```bash
ssh bolt-remote
sudo systemctl stop llama-server.service
pkill -f "llama-server.*--port 8081"        # 关键：必须停掉这个，否则数据全是污染的
nvidia-smi --query-compute-apps=pid,used_memory --format=csv   # 必须只剩 1 MiB
B=~/llama-cpp-sm70/build/bin
$B/llama-server -m ~/models/translategemma-4b-it.i1-Q4_K_M.gguf \
  --lora ~/models/translategemma-4b-LoRA-COK-T4.gguf \
  -ngl 99 -c 1024 --parallel 1 -ctk f16 -ctv f16 \
  --jinja --chat-template-file ~/translategemma-official.jinja \
  --alias default --port 8099
# 然后发官方格式请求，读 timings.predicted_per_token_ms
```

**方法学要点：**
- 每配置先发一次请求预热（丢弃首个样本）——冷时钟让首个请求慢 37%（27.25 vs 19.87 ms/tok）
- 用 `predicted_per_token_ms` 而不是墙钟（自己算墙钟容易出错，本次踩过）
- 长段落请求（~250 token 输出）比短句稳定得多；短句用「连发 N 次」看趋势
