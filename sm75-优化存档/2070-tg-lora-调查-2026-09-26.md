# 2070 部署优化调查：TranslateGemma-4B + COK LoRA（2026-09-26）

机器：10.1.2.16（RTX 2070 / sm_75 / 8 GB），生产跑 `llama-server` + `llama-gateway`。
模型：`translategemma-4b-it.i1-Q4_K_M.gguf`（gemma3，34 层，8 Q / 4 KV 头 = GQA 2，
D=256，`sliding_window=1024`，**无 `nextn_predict_layers` = 没有 MTP 头**）
服务：`-c 1024 --parallel 2`，运行期 LoRA `translategemma-4b-LoRA-COK-T4.gguf`
（7 个 target × 34 层 × 2 = **476 个张量**），官方 jinja 模板 + **JSON schema 约束**。
网关：`MAX_CONCURRENCY=7`，`TIMEOUT=2500ms`。

**本文件是一次完整调查的结论，含被推翻的假设。下次不要重跑。**

## 最重要的一条（先看这个）

请求里的 `response_format` JSON schema 和 LoRA 的训练数据**不匹配**：训练时 assistant
侧输出的是**裸译文**，部署却要它输出 JSON 对象。后果是 ~35% 输出是垃圾或训练数据占位符
（`{ 渔场 }`、`{ 翻译内容 }`），`temperature: 0` 下**确定性地**输出 `:{ 渔场`。

**去掉 `response_format`**（客户端直接把 `choices[0].message.content` 当译文）：
5 样本 x 20 次 = **100/100 全对、确定性**，token 从 51 降到 9，`predicted_ms`
从 ~1400 降到 **108**（快 13-17 倍），网关 2.5 s 超时从 ~7% 触发变为 10 倍余量。
**不需要改 llama.cpp。** 详见第 6 节。

## 2. 运行期 LoRA 的真实代价（源码级 + 实测）

`src/llama-graph.cpp:1534 build_lora_mm`，每个适配器每步往图里加：

```cpp
ab_cur = ggml_mul_mat(ctx0, lw->b, ggml_mul_mat(ctx0, lw->a, cur));  // 2 matmul
ab_cur = ggml_scale(ctx0, ab_cur, scale);                            // SCALE
res    = ggml_add(ctx0, res, ab_cur);                                // ADD
```

238 个适配器 → 每步 **476 个额外 matmul + 476 个 elementwise**。
base 本身只有 238 个 matmul → **matmul 数变成 3 倍**，而 LoRA 矩阵极小（rank 128
vs 5120 维，FLOPs 只占 ~2%）→ 纯调度开销。

实测（同配置、交替）：

| | prefill | decode |
|---|---|---|
| base（无 LoRA）| **600 tok/s** | 20.35 ms/tok |
| base + 运行时 LoRA | 430 tok/s（**-28%**）| 25.0 ms/tok（**+23%**）|

## 3. ❌ 合并 LoRA：一笔打平的账（**别再试**）

### 3.1 合并本身是对的

`llama-export-lora` → F16 → 再量化。隔离测试（同一请求，三个模型）：

| | 输出 | 质量 |
|---|---|---|
| A: base + 运行时 LoRA | `把他盟里的资源都清了` | ✅ |
| **B: F16 合并（未量化）** | `把他盟里的资源都清了` | ✅ **与 A 逐字相同** |
| C: 合并 + Q4_K_M | `培养他的同族成员` | ❌ |

**所以合并没有错，坏的是重定量。**

### 3.2 无 imatrix 重定量 → 质量崩

原因：**LoRA 的 delta 很小（rank 128 / alpha 128），合并进权重再量化时会被量化误差抹掉。**

用基座模型（Q4_K_M）+ 17886 条翻译对（`tg_calib.txt`，~369K token）算 imatrix
（`PPL = 27.1333 ± 0.46670`，4 分钟），再量化：

| 精度 | 大小 | s0（en→zh）| s1 | s2 |
|---|---|---|---|---|
| A: base+LoRA | — | `把他盟里的资源都清了` ✅ | ✅ | ✅ |
| i1-Q4_K_M | 2.49 GB | `:{ ïd_l_lang_code` ❌ | ✅ | ✅ |
| i1-Q5_K_M | 2.83 GB | `+ { 别sourcename` ❌ | ✅ | ✅ |
| **i1-Q6_K** | 3.19 GB | `把他盟里的资源都清了` ✅ | ✅ | ✅ |

非单调（Q5 崩、Q6 好）说明是**特定张量的精度**在起作用，不是整体位数。

### 3.3 但 Q6_K 合并**没有速度收益**

同一请求交替 2 轮 × 3 次：

| | 合计均值 |
|---|---|
| A: base + 运行时 LoRA | **21.4 ms/tok** |
| B: merged i1-Q6_K | **21.9 ms/tok** |

**去掉 LoRA 内核省下的时间，恰好被 Q6_K 多出的 28% 字节吃掉。**

### 3.4 结论

**合并这条路买不到东西。** Q4 快但质量崩；Q6 质量好但不快。保留运行期 LoRA。

## 4. ❌ 全部排除的杠杆

| 杠杆 | 结论 |
|---|---|
| `-ub 2048`（V100 上 +20~37%）| **不适用**：`should_use_mmq` 对 Turing 提前 `return true`，走 mmq 融合路径，没有重复解压 |
| TurboQuant KV | 上下文仅 512，KV ~4 MB，无关 |
| MTP 投机 | 模型**没有 MTP 头**；外挂 draft 需 vocab 兼容的 Gemma-3 小模型，且输出很短（6~15 token）|
| CUDA graph | **已在生效**（`graphs reused = 334`）|
| 换二进制 | **无差异**：3 轮 9.99 vs 10.97 ms/tok，REPO 被一个 13.33 的离群值抬高，去掉后两边都 ~9.8 |
| 折 `scale` 进 `lw->b` | **无价值**：本 fork 的 `GGML_CUDA_FUSE_CHAIN`（`ggml-cuda.cu:3616-3619`）已把 SCALE+ADD 融成一个内核 |

## 5. ⚠️ 被本调查推翻的三个说法（记录在案）

1. **「生产二进制快 32%」** —— 单轮离群值（13.33 ms/tok）造成，三轮后两边一致
2. **「量化域内合并（逐 block 反量化→加 delta→同类型重量化）是答案」** ——
   与「F16 合并再量化」**数学等价**，同样会毁掉 delta
3. **「折 scale 可省 238 个内核」** —— `FUSE_CHAIN` 已经融合了

## 6. ✅ 已解决：请求格式与训练数据不匹配（**本次最大发现**）

### 6.1 症状

生产路径（经网关 7080）同一请求 20 次：

| 输出 | 次数 |
|---|---|
| `把他盟里的资源号都清了`（正确）| 8 |
| `把他盟里的资源都清了`（正确）| 5 |
| `清空同伴资源` / `清空同伴` / `清空盟里的资源`（错）| 3 |
| `{ 茂菜语` / `{ 翱source_lank_code` / `{ 艾特}`（垃圾）| 3 |
| 空 | 1 |

**35% 错误或垃圾**，而且 `temperature: 0` 下 **30/30 完全相同地输出 `:{ 渔场`** ——
**不是不确定，是贪心路径本身就坏**。正确译文只是采样时碰运气抽到的。

### 6.2 根因：LoRA 被训练成输出**纯译文**，部署却要它输出 **JSON**

训练数据（`~/tg_train.jsonl`，7.3 上，17886 条）：

```json
{"messages":[
  {"role":"user","content":"{\"source_lang_code\": \"auto\", \"target_language_code\": \"uk\", \"text\": \"dead castle\"}"},
  {"role":"assistant","content":"Мертвий замок"}
]}
```

**assistant 侧是裸译文，不是 JSON。** 而部署的请求带
`response_format: {type: json_object, schema: {source_lang_code, target_language_code, translation}}`
—— 模型在「填 JSON 模板」，填不进去就吐训练数据里的**占位符**：
`{ 资源名称 }`、`{ 目标语言 }`、`{ 翻译内容 }`、`{ 渔场 }`。

另外训练数据里 `source_lang_code` 大量是 **`"auto"`**，但部署的服务**拒绝 `auto`**
（`T4 requires an explicit source_lang_code (use LID)`）—— 第二处不匹配。

### 6.3 修复：去掉 `response_format`

`temperature: 0`，同一请求：

| | 带 `response_format`（现状）| **去掉 `response_format`** |
|---|---|---|
| s0 en→zh | `{ "source_lang_code" :":{ 渔场",...` ❌ 51 token | **`把他盟里的资源号都清了`** ✅ 9 token |
| s1 es→en | JSON 外壳，43 token | `if we combine the two alliances we would be...` ✅ 13 token |
| s2 de→en | JSON 外壳，40 token | `I have to sell my other farms right now` ✅ 10 token |

5 样本 x 20 次 = **100/100 全对、20/20 完全一致（确定性）**：

| 样本 | 输出 | token | `predicted_ms` |
|---|---|---|---|
| s0 en→zh | `把他盟里的资源号都清了` | 9 | **108** |
| s1 es→en | `if we combine the two alliances we wou...` | 13 | 162 |
| s2 de→en | `I have to sell my other farms right no...` | 10 | 122 |
| s3 en→zh | `现在攻击敌方基地` | 6 | 70 |
| s4 zh-Hans→en | `I don't know if I can do it.` (错) | 12 | 150 |

**51 token / ~1400-1900 ms / ~50% 垃圾 -> 9 token / 108 ms / 100% 正确，快 13-17 倍。**

**修复方式**：客户端不传 `response_format`，直接把 `choices[0].message.content`
当作译文。**这是配置/客户端改动，不需要改 llama.cpp。**

### 6.4 未决：s4（中文作源语言）确定性地答错

`我们需要更多资源` -> `I don't know if I can do it.`，20/20 一致。
加上模型曾吐 `The source language is not supported` / `You can't chat again in {0} after...`
这类**审核答复**文本，判断 **`zh-Hans` 作源语言码不在 LoRA 训练分布里**
（训练数据用的是 `en`/`es`/`de`/`uk` 这类短码）。需要确认业务是否真的要求中译外。

## 7. ✅ 已解决：网关超时（原「延迟抖动」现象）

原以为的「无解释的 ±40% 抖动」，实际是两个独立事实叠加：

1. **每 token 时间确实会抖**：`predicted_per_token_ms` 实测 **16.99 - 30.67 ms/tok**（1.8 倍）。
2. **网关 2.5 s 超时真的在触发**：抓到原始响应体 `{"error":"timeout"}`，
   约 **7%** 的请求这样失败。`predicted_ms` 达 **1874 ms**，逼近 2500 ms 线。

**去掉 `response_format` 后输出从 51 token 降到 9 token**，`predicted_ms` 从 ~1400 ms
降到 **108 ms** —— 对 2500 ms 超时有 **10 倍余量**，超时问题消失。

（每 token 那 1.8 倍抖动是 2070 自身的时钟/温度行为，生成短 5 倍后其影响也随之缩小。）

## 9. 方法学备注

- **生产服务要求请求带 `model` 字段**，且官方模板要求 **官方语言码**（`zh-Hans` 而非 `zh-CN`）。
  发错会得到 400 而不是可用的计时。注意 `zh-Hans` 虽被模板接受，但**可能不在 LoRA 的
  训练分布里**（见 6.4）。
- 生产模型对**纯文本 `/completion`** 会立刻输出 1 个 token 就停（T4 依赖官方模板格式），
  用那种请求测速度会得到 `pred_n=1` 的无效数据。
- 首请求的 pp 明显偏高（411 vs 43），是 CUDA graph 首次捕获；**必须丢弃首个样本**。
- **比较两个二进制是否行为一致时，两边各跑 12 次同一请求就够**：本仓库构建与部署二进制
  在 temp 0 下都是 12/12 `:{ 渔场`，一次就证明问题不在构建上。
- **调质量问题时先打 `temperature: 0`**。采样会掩盖贪心路径的缺陷 —— 本次就是因为默认
  `temp 0.8` 让「~50% 正确」看起来像「不确定」，实际贪心路径 100% 输出垃圾。
- 两机（7.3 与 10.1.2.16）**不能直连**，经 Mac 中转的链路只有 **2.35 MB/s** ——
  2.7 GB 要 20 分钟，设计实验时避免跨机传输。
