# 2070 部署优化调查：TranslateGemma-4B + COK LoRA（2026-09-26）

机器：10.1.2.16（RTX 2070 / sm_75 / 8 GB），生产跑 `llama-server` + `llama-gateway`。
模型：`translategemma-4b-it.i1-Q4_K_M.gguf`（gemma3，34 层，8 Q / 4 KV 头 = GQA 2，
D=256，`sliding_window=1024`，**无 `nextn_predict_layers` = 没有 MTP 头**）
服务：`-c 1024 --parallel 2`，运行期 LoRA `translategemma-4b-LoRA-COK-T4.gguf`
（7 个 target × 34 层 × 2 = **476 个张量**），官方 jinja 模板 + JSON schema 约束。
网关：`MAX_CONCURRENCY=7`，`TIMEOUT=2500ms`。

**本文件是一次完整调查的结论，含被推翻的假设。下次不要重跑。**

## 1. 已落地：去掉 `--cache-type-k/v q8_0`

| | 受控 A/B（同一二进制、同参数、交替 3 轮）|
|---|---|
| f16 KV | **17.25 ms/tok** |
| q8_0 KV | 20.35 ms/tok（**+18%**）|
| prefill | 无差异（596~612 tok/s）|

512 上下文下 f16 KV 才 ~4 MB，显存完全够，而且精度更高 → 无风险。

（version 10830 / `a3d5603d1`），**不是本仓库构建**（10828 / `074306db5`），

## 2. 运行期 LoRA 的真实代价（源码级 + 实测）

`src/llama-graph.cpp:1534 build_lora_mm`，每个适配器每步往图里加：

```cpp
ab_cur = ggml_mul_mat(ctx0, lw->b, ggml_mul_mat(ctx0, lw->a, cur));  // 2 matmul
ab_cur = ggml_scale(ctx0, ab_cur, scale);                            // SCALE
res    = ggml_add(ctx0, res, ab_cur);                                // ADD
```

238 个适配器 → 每步 **476 个额外 matmul + 476 个 elementwise**。
base 本身只有 238 个 matmul → **matmul 数变成 3 倍**，而 LoRA 矩阵极小（rank 128
vs 5120 维，FLOPs 只占 ~2%）→ 纯调度开销。

实测（同配置、交替）：

| | prefill | decode |
|---|---|---|
| base（无 LoRA）| **600 tok/s** | 20.35 ms/tok |
| base + 运行时 LoRA | 430 tok/s（**-28%**）| 25.0 ms/tok（**+23%**）|

## 3. ❌ 合并 LoRA：一笔打平的账（**别再试**）

### 3.1 合并本身是对的

`llama-export-lora` → F16 → 再量化。隔离测试（同一请求，三个模型）：

| | 输出 | 质量 |
|---|---|---|
| A: base + 运行时 LoRA | `把他盟里的资源都清了` | ✅ |
| **B: F16 合并（未量化）** | `把他盟里的资源都清了` | ✅ **与 A 逐字相同** |
| C: 合并 + Q4_K_M | `培养他的同族成员` | ❌ |

**所以合并没有错，坏的是重定量。**

### 3.2 无 imatrix 重定量 → 质量崩

原因：**LoRA 的 delta 很小（rank 128 / alpha 128），合并进权重再量化时会被量化误差抹掉。**

用基座模型（Q4_K_M）+ 17886 条翻译对（`tg_calib.txt`，~369K token）算 imatrix
（`PPL = 27.1333 ± 0.46670`，4 分钟），再量化：

| 精度 | 大小 | s0（en→zh）| s1 | s2 |
|---|---|---|---|---|
| A: base+LoRA | — | `把他盟里的资源都清了` ✅ | ✅ | ✅ |
| i1-Q4_K_M | 2.49 GB | `:{ ïd_l_lang_code` ❌ | ✅ | ✅ |
| i1-Q5_K_M | 2.83 GB | `+ { 别sourcename` ❌ | ✅ | ✅ |
| **i1-Q6_K** | 3.19 GB | `把他盟里的资源都清了` ✅ | ✅ | ✅ |

非单调（Q5 崩、Q6 好）说明是**特定张量的精度**在起作用，不是整体位数。

### 3.3 但 Q6_K 合并**没有速度收益**

同一请求交替 2 轮 × 3 次：

| | 合计均值 |
|---|---|
| A: base + 运行时 LoRA | **21.4 ms/tok** |
| B: merged i1-Q6_K | **21.9 ms/tok** |

**去掉 LoRA 内核省下的时间，恰好被 Q6_K 多出的 28% 字节吃掉。**

### 3.4 结论

**合并这条路买不到东西。** Q4 快但质量崩；Q6 质量好但不快。保留运行期 LoRA。

## 4. ❌ 全部排除的杠杆

| 杠杆 | 结论 |
|---|---|
| `-ub 2048`（V100 上 +20~37%）| **不适用**：`should_use_mmq` 对 Turing 提前 `return true`，走 mmq 融合路径，没有重复解压 |
| TurboQuant KV | 上下文仅 512，KV ~4 MB，无关 |
| MTP 投机 | 模型**没有 MTP 头**；外挂 draft 需 vocab 兼容的 Gemma-3 小模型，且输出很短（6~15 token）|
| CUDA graph | **已在生效**（`graphs reused = 334`）|
| 换二进制 | **无差异**：3 轮 9.99 vs 10.97 ms/tok，REPO 被一个 13.33 的离群值抬高，去掉后两边都 ~9.8 |
| 折 `scale` 进 `lw->b` | **无价值**：本 fork 的 `GGML_CUDA_FUSE_CHAIN`（`ggml-cuda.cu:3616-3619`）已把 SCALE+ADD 融成一个内核 |

---

## 5. ⚠️ 被本调查推翻的三个说法（记录在案）

1. **「生产二进制快 32%」** —— 单轮离群值（13.33 ms/tok）造成，三轮后两边一致
2. **「量化域内合并（逐 block 反量化→加 delta→同类型重量化）是答案」** ——
   与「F16 合并再量化」**数学等价**，同样会毁掉 delta
3. **「折 scale 可省 238 个内核」** —— `FUSE_CHAIN` 已经融合了

---

## 6. 🔍 两个未查的现象（可能是比 LoRA 更大的问题）

1. **单请求延迟抖动 ±40%**（16.8~32.4 ms/tok），而 `/metrics` 显示
   `n_busy_slots_per_decode = 0`、`requests_processing = 0` —— **不是并发流量**。
   对一个 `TIMEOUT=2500ms` 的翻译服务，这比 LoRA 更值得关注。
2. **同一 `temperature 0` 请求结果会变**（`资源` vs `资源号`），可能与
   grammar 约束采样或 slot 缓存状态有关。

## 8. 方法学备注

- **生产服务要求请求带 `model` 字段**，且官方模板要求 **官方语言码**（`zh-Hans` 而非 `zh-CN`），
  且 T4 **不接受 `source_lang_code: auto`**。发错会得到 400 而不是可用的计时。
- 生产模型对**纯文本 `/completion`** 会立刻输出 1 个 token 就停（T4 依赖官方模板格式），
  用那种请求测速度会得到 `pred_n=1` 的无效数据。
- 首请求的 pp 明显偏高（411 vs 43），是 CUDA graph 首次捕获；**必须丢弃首个样本**。
- 两机（7.3 与 10.1.2.16）**不能直连**，经 Mac 中转的链路只有 **2.35 MB/s** ——
  2.7 GB 要 20 分钟，设计实验时避免跨机传输。
